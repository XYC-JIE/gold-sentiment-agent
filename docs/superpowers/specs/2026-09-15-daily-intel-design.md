# 金银舆情 AI 监控系统 — 设计文档

日期：2026-09-15
状态：已确认，待拆实施计划

---

## 一、背景与目标

### 1.1 项目目的

**这是一个自用工具。** 用户持续关注 AI 前沿动态，同时需要及时了解影响金银走势的宏观消息（加息降息、通胀、就业数据等），希望在手机上每天一次性拿到经过筛选和解读的摘要，而不是自己刷十几个源。

设计判据是：

1. 每天早上收到的东西，**我是否真的会看**——它是否比我自己刷源更省时间
2. 长期积累下来的数据，**对我判断金银是否真有帮助**

### 1.2 非目标

- 不做实时高频快讯（不做自建金十）
- 不做交易信号或投资建议
- 不做 Web 交互式分析平台（静态看板足够）

## 二、功能需求

### 2.1 用户可见行为

每天早上约 07:30（北京时间），飞书机器人推送一份日报卡片，包含：

1. **AI 前沿** 3–5 条，每条含标题、一句"为什么重要"、原文链接
2. **金银聚焦** 3–5 条，每条标注影响方向与强度；含当日情绪指数与多空倾向
3. **今日紧盯** 宏观日历（议息、CPI、非农等）
4. **看板链接**

同时仓库内数据与图表持续积累，可供回溯与趋势观察。

### 2.2 输入源（中英混合）

**AI 前沿（英文）**：OpenAI News、Anthropic News、Google DeepMind Blog、Hacker News、arXiv cs.AI、Hugging Face Daily Papers

**AI 前沿（中文）**：机器之心、量子位

**金融（中文）**：金十数据快讯、华尔街见闻

**金融（英文）**：CNBC Markets、美联储官方新闻稿

**金价**：stooq.com 日线 CSV（XAUUSD，免费无 key）

> 实施第一步必须逐个验证源的可用性（RSS 地址会变更、部分站点反爬）。所有源地址集中写在 `config/sources.yaml`，失效时替换配置即可，不改代码——这正是配置外置的目的。

## 三、整体架构

```
GitHub Actions（cron 每天 23:30 UTC = 次日 07:30 北京时间）
   │
   ① 采集    Python 抓取各源 → 清洗去重 → raw_items
   │
   ② 智能    调用 Dify Workflow API
   │          Dify 内做 LLM 结构化抽取 + 日报文案生成
   │          返回结构化 JSON
   │
   ③ 计算    追加 events → 计算情绪指数 → Matplotlib 出图
   │
   ④ 分发    飞书机器人推送卡片
   │
   ⑤ 沉淀    git commit 数据与图表；生成静态看板并部署 Pages
```

### 3.1 分层职责（核心设计决策）

| 层 | 承担 | 选择理由 |
|---|---|---|
| **Dify** | LLM 编排：结构化抽取、日报生成、Prompt 迭代 | 可视化画布 + 逐节点运行日志可观测；改 Prompt 无需改代码重新部署；LLM 节点可绑定 JSON Schema 约束输出格式 |
| **Python** | 采集、存储、指标计算、出图 | Dify 代码节点是受限沙箱，无 pandas/matplotlib 且不能持久化文件 |
| **GitHub Actions** | 定时调度、结果回写 | 免费额度充足；运行在海外，无需代理即可访问墙外信源；不依赖本机开机 |

**为什么不用 Python 直接调 LLM API、绕过 Dify**：Dify 提供的是可观测、可迭代的编排层。逐节点输入输出与 token 消耗可查，Prompt 迭代不需要改代码和重新部署，结构化输出有 Schema 保证比手写 JSON 解析更稳。

**为什么采集和计算不放进 Dify**：Dify 的代码节点沙箱跑不了 pandas/matplotlib，也不能持久化文件到仓库。这是工具能力边界问题，不是设计取舍。

## 四、Dify 工作流设计

五个节点：

```
开始节点（输入 raw_items、date）
  ↓
代码节点：预筛去重 + 每条截断 800 字（控制 token）
  ↓
LLM 节点 A：结构化抽取（JSON Schema 约束）
  ↓
LLM 节点 B：日报文案生成
  ↓
结束节点（返回结构化 JSON）
```

### 4.1 LLM 节点 A 输出结构

每条事件：

| 字段 | 说明 |
|---|---|
| `event_type` | **枚举**：货币政策 / 经济数据 / 地缘政治 / 央行购金 / 美元走势 / 通胀 / 就业 / 其他 |
| `direction` | 利多金银 / 利空金银 / 中性 |
| `strength` | 1–5 整数 |
| `summary` | 中文一句话摘要 |
| `source` / `url` / `published_at` | 溯源信息 |

`event_type` 限定为枚举而非自由文本，否则后续统计时分类会散得无法聚合。

### 4.2 LLM 节点 B 输出结构

- AI 要闻 3–5 条（标题 + "为什么重要"）
- 金银聚焦 3–5 条（含方向与强度）+ 综合判断
- 今日宏观日历

### 4.3 工作流 DSL 导出

Dify 工作流导出为 `dify/daily-intel-workflow.yml` 提交进仓库。这首先是**备份**：工作流在 Dify Cloud 上误删或改坏时可直接导入还原，不必凭记忆重建。附带好处是工作流的每次调整都有版本记录可查。

## 五、数据模型与指标定义

两张表，均为每日追加、只增不改。

### 5.1 `data/events.csv`（原始资产）

```
date, event_type, direction, strength, summary, source, url, published_at
```

### 5.2 `data/daily_index.csv`（计算产物）

```
date, sentiment_score, bull_count, bear_count, total_events, gold_close
```

### 5.3 情绪指数定义

每条事件赋予符号：利多 `+1`、利空 `-1`、中性 `0`。

```
sentiment_score = Σ(符号 × strength) / (5 × 事件数)
```

**归一化理由**：除以 `5 × n` 使取值落入 `[-1, 1]`，从而让事件数量不同的日期之间可比。直接求和会导致"新闻多的一天天然分高"，那测的是信息流量而非市场情绪。

### 5.4 金价对照

`gold_close` 抓取 stooq.com 的 XAUUSD 日线。**该列是本项目分析价值的支点**：只有与真实金价并排，才能回答"这个指数是否具备信息量"。缺少它，情绪指数只是一个自娱自乐的分数。

### 5.5 指标可信度验证

LLM 的抽取结果直接决定了指数是否可用。如果 `direction` 判错，指数会给出错误的多空倾向，而**这个错误看起来和正确结果一模一样**——没有任何报错，只有一张看起来合理的折线图。自用项目对这种情况没有任何容错余地，因为唯一的消费者就是自己。

因此单独安排一个阶段做验证：

- 随机抽取 50 条事件，**人工逐条标注**作为金标准
- 计算 `event_type` 分类准确率、`direction` 判断准确率
- 输出混淆矩阵，结果记录在 `docs/` 下

准确率不达标时的对策（按优先级）：补充 Few-shot 示例 → 收紧 `event_type` 枚举定义 → 调整 Prompt 判据 → 若某类事件持续误判，则将其并入"其他"。

## 六、图表与分发产物

三张图，存 `charts/`：

1. 近 30 日情绪指数折线（带 0 轴基准）
2. 近 7 日事件类型分布
3. **情绪指数 vs 金价双轴图** — 用于观察两者是否同步，这是判断指数到底有没有用的主要依据

### 6.1 飞书卡片形态

飞书自定义机器人的富文本要内嵌图片，必须先将图片上传飞书换取 `image_key`，而上传接口需要自建应用凭证，webhook 机器人无法做到。

因此**第一版为纯文字卡片**；看板页就绪后，在卡片末尾附上可点击的链接（见 6.2）。真内嵌图片需升级为飞书自建应用，列为可选增强，不影响项目主体价值。

### 6.2 静态看板页

Actions 跑完生成静态 HTML 部署到 GitHub Pages。用途有两个：手机上随时翻历史趋势，比在飞书里翻聊天记录方便得多；飞书卡片里可以直接给一个可点击的链接。

## 八、错误处理

**总原则：任何情况下都必须有输出**，最差降级为纯标题列表。一个每日送达的东西，静默失败远比推得难看严重。

| 故障 | 处理策略 |
|---|---|
| 单个源抓取失败 | 各采集器独立 try/except 互不影响，日报中标注"N 个源失败" |
| Dify 调用失败 | 重试 2 次（指数退避）；仍失败则发飞书纯文本告警，绝不静默 |
| LLM 返回非法 JSON | Dify 侧 JSON Schema 约束 + 重试一次；Python 侧二次校验，丢弃坏条目而非整体崩盘 |
| Actions 任务失败 | 依赖 GitHub 自带的失败邮件通知 |

## 十一、已知局限

清楚局限是使用指标的前提，否则会误信自己造出来的结论：

- LLM 抽取存在误差，已量化（见 5.5）
- `strength` 的 1–5 由模型主观判断而非拟合得出，故指数是**相对指标**：可用于比较趋势，不可当作绝对刻度读
- 情绪与金价是**相关性而非因果**；金价同时受实际利率、美元指数、避险需求等多重因素驱动
- 单日事件量仅数条量级，统计功效有限，不可用于高频推断
- 信源可能失效或改版，需持续维护

## 十二、实施阶段

| 阶段 | 内容 | 预估 |
|---|---|---|
| 0 | 环境准备：GitHub 仓库、飞书机器人 Webhook、DeepSeek Key、Dify 账号 | 0.5 天 |
| 1 | 采集层：`collectors/` + `sources.yaml` + mock 测试，逐个验证源可用性 | 1 天 |
| 2 | Dify 工作流：搭建、调通、导出 DSL、接通 API | 1 天 |
| 3 | 计算与图表：`analysis.py`（TDD）+ `charts.py` | 0.5 天 |
| 4 | 推送与调度：`notifier.py` + Actions + Secrets 配置 | 0.5 天 |
| — | **里程碑：每天早上能收到日报（阶段 0–4 累计）** | 3.5 天 |
| 5 | 准确率验证（50 条人工标注 + 混淆矩阵）——保证指标可信 | 1 天 |
| 6 | 静态看板页 + Pages 部署——提升自用体验 | 0.5 天 |

合计约 5 天工作量（按每天 2–3 小时投入）。

**阶段顺序理由**：0→4 打通完整链路，先让工具真的能用起来——只有开始每天看，才能发现设计里真正别扭的地方。阶段 5 之所以排在能用之后而不是砍掉，是因为**指数一旦用于自己的判断，就必须知道它有多准**，否则一个看起来合理的错误折线图会持续误导你。阶段 6 属于体验优化，可以推迟。

**不做的事**：README 不做专门打磨，随代码随手写。等工具用得顺手了再补，成本同样很低。
